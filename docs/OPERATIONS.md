# Operations guide

Internal guide for deploying and running Ghanjah. Never put real values (keys, passwords,
connection strings) in this repository; keep them in the hosting provider's environment settings
or in the server's `.env` file.

## 1. Components

| Component | Purpose |
|---|---|
| Web service | API and web application, built from the root `Dockerfile` |
| PostgreSQL | Application database |
| AI provider | Any OpenAI-compatible chat-completions endpoint (hosted, or self-hosted with Ollama) |
| Meta (optional) | WhatsApp Cloud API and Instagram messaging channels |

## 2. Deploying on Render

Prerequisites: a PostgreSQL database (connection string), an API key from the AI provider, and
access to the GitHub repository.

1. In Render, choose **New > Blueprint** and select this repository. Render reads `render.yaml`.
2. Enter the values Render asks for (`DATABASE_URL`, `SYSTEM_ADMIN_EMAIL`,
   `SYSTEM_ADMIN_PASSWORD`, `LLM_API_KEY`). `SECRET_KEY` and `WHATSAPP_VERIFY_TOKEN` are
   generated by Render.
3. Deploy. When the service is **Live**, sign in with the system administrator account.
4. In **Platform settings**, use **Test AI** to confirm the AI provider is reachable.
5. Before onboarding real customers, set `SEED_DEMO_DATA=false` and delete the demo company.
6. Optional: add a custom domain under the service's **Settings > Custom Domains**.

The system administrator account is created on the first start only. Change its password later
from **My account**, not through the environment variable.

## 3. Self-hosted server (alternative)

On an Ubuntu or Debian server with a domain pointing to it:

```bash
git clone <repository-url> ghanjah && cd ghanjah
sudo bash deploy/install.sh
```

The installer installs Docker if needed, asks for the domain, the administrator login and the AI
provider, writes `.env` with generated secrets, and starts the stack with automatic HTTPS. It can be
run again to change any answer.

| Task | Command |
|---|---|
| Status | `docker compose ps` |
| Logs | `docker compose logs -f backend` |
| Restart | `docker compose restart` |
| Stop (data is kept) | `docker compose down` |

## 4. Environment variables

All configuration is read from environment variables. `.env.example` lists the variables used by
Docker Compose.

### Application

| Variable | Purpose |
|---|---|
| `ENVIRONMENT` | `production` on any public deployment, `development` locally |
| `SECRET_KEY` | Signing key for sessions; long random value, never shared |
| `ENCRYPTION_KEY` | Optional key for encrypting stored credentials; derived from `SECRET_KEY` when empty |
| `DATABASE_URL` | PostgreSQL connection string |
| `SYSTEM_ADMIN_EMAIL` | Login of the platform administrator (first start only) |
| `SYSTEM_ADMIN_PASSWORD` | Initial password of the platform administrator (first start only) |
| `SYSTEM_ADMIN_NAME` | Display name of the platform administrator |
| `SEED_DEMO_DATA` | `true` creates a demo company; `false` for real deployments |
| `CORS_ORIGINS` | Allowed browser origins, comma separated |
| `TRUSTED_PROXY_HOPS` | Number of reverse proxies in front of the application |
| `BCRYPT_ROUNDS` | Password hashing cost |

### AI provider

| Variable | Purpose |
|---|---|
| `LLM_PROVIDER` | `openai_compatible` (or `mock` for a demo without a model) |
| `LLM_BASE_URL` | Base URL of the provider's API |
| `LLM_API_KEY` | Provider API key |
| `LLM_MODEL` | Model name |
| `LLM_FALLBACK_MODELS` | Optional backup models, comma separated |
| `LLM_REASONING_EFFORT` | Optional, for reasoning models |
| `LLM_TEMPERATURE` | Sampling temperature |
| `LLM_MAX_HISTORY_MESSAGES` | Conversation history sent to the model |

AI settings can also be changed at runtime in **Platform settings**; a value saved there takes
precedence over the environment.

### Messaging (Meta)

| Variable | Purpose |
|---|---|
| `WHATSAPP_VERIFY_TOKEN` | Verify token for the shared WhatsApp webhook |
| `WHATSAPP_APP_SECRET` | App secret of the shared Meta app |
| `WHATSAPP_API_VERSION` | Graph API version |
| `WHATSAPP_DEFAULT_ACCESS_TOKEN` | Optional access token of the shared Meta app |

### Docker Compose only

| Variable | Purpose |
|---|---|
| `COMPOSE_PROFILES` | Optional services: `https` (Caddy), `local-ai` (Ollama) |
| `DOMAIN` | Public domain used for HTTPS |
| `WEB_PORT`, `WEB_BIND` | Port and bind address of the web container |
| `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` | Database container credentials |
| `BASE_MODEL` | Base model pulled by the `local-ai` profile |

## 5. Connecting WhatsApp and Instagram

Each agency connects its own channels from the dashboard (**AI & channels**). At a high level:

1. In the Meta developer portal, create or use a Business app and add the **WhatsApp** and/or
   **Instagram** product.
2. Copy the required identifiers and credentials from Meta (phone number ID or Instagram account,
   a long-lived access token, and the app secret) into **AI & channels** and save.
3. The same page shows the callback URL and verify token for that agency. Enter both in the app's
   webhook configuration in Meta and subscribe to **messages**.
4. Send a test message to confirm the conversation appears in **Conversations**.

To serve several agencies from one platform-owned Meta app, set `WHATSAPP_APP_SECRET` and
`WHATSAPP_VERIFY_TOKEN` and configure the shared webhook shown in **Platform settings**.

WhatsApp only allows free-form replies within 24 hours of the customer's last message.

## 6. Backups

- **Managed PostgreSQL:** enable the provider's backups or point-in-time restore, and export a dump
  periodically (`pg_dump "$DATABASE_URL" | gzip > backup.sql.gz`).
- **Self-hosted:** `sudo bash deploy/backup.sh` writes a compressed dump to `backups/` and keeps the
  latest 14. Schedule it daily with cron and copy the files off the server.
- Test a restore regularly. Store backups encrypted and with restricted access; they contain
  customer data.

## 7. Updating

- **Render:** every push to the deployed branch is built and deployed automatically. Check
  **Events** for a failed deploy; use **Manual Deploy > Deploy latest commit** if needed.
- **Self-hosted:** `sudo bash deploy/update.sh` pulls the latest code and restarts the stack. Data
  is kept.
- Take a backup before any update that changes the database.
